# Smart Query Language Validator

A Theory of Computation college project: a small, working compiler
front-end for a SQL-like query language. Type a query and watch it get
scanned into tokens, walked through a hand-built finite automaton, and
checked against a context-free grammar — every step is real, computed
code, not a mock.

```
SELECT name FROM students WHERE age > 18;
```

No external SQL parser is used and no query is ever executed. Every
token, DFA state transition and grammar rule comes from this project's
own Python code.

## How to run the project

### 1. Backend (FastAPI)

```bash
cd backend
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env            # optional, defaults already work
uvicorn app.main:app --reload --port 8000
```

The API is now live at `http://localhost:8000`.
Interactive API docs (auto-generated by FastAPI): `http://localhost:8000/docs`

**Run the backend tests:**
```bash
cd backend
pytest -v
```
All 34 tests should pass (lexer, DFA, grammar, and full API integration tests).

### 2. Frontend (React + Vite)

In a **second terminal**:

```bash
cd frontend
npm install
cp .env.example .env            # points the app at http://localhost:8000
npm run dev
```

Open `http://localhost:5173` in your browser. The Dashboard, Query
Validator, DFA Visualizer, and About pages are all in the left sidebar.

### 3. Production build (optional)

```bash
cd frontend
npm run build      # outputs static files to frontend/dist
npm run preview    # serve the production build locally
```

## API reference

| Method | Endpoint          | Description                                          |
|--------|-------------------|-------------------------------------------------------|
| GET    | `/health`         | Liveness check                                        |
| POST   | `/api/tokenize`   | Runs the lexer only; returns the token list            |
| POST   | `/api/validate`   | Runs lexer + CFG parser; returns valid/invalid, tokens, errors, grammar trace |
| POST   | `/api/dfa-check`  | Runs a single string through the identifier or number DFA (powers the DFA Visualizer) |

Example:
```bash
curl -X POST http://localhost:8000/api/validate \
  -H "Content-Type: application/json" \
  -d '{"query": "SELECT name FROM students WHERE age > 18;"}'
```

## Theory of Computation concepts used (for the viva)

**1. Regular Expressions**
Every token type — `SELECT`/`FROM`/`WHERE` (KEYWORD), identifiers,
numbers, strings, operators, punctuation — is defined by a regular
expression in `backend/app/lexer.py`. A regular expression describes a
*regular language*: the simplest class of language in the Chomsky
hierarchy, closed under union, concatenation, and Kleene star.

**2. Finite Automata**
By **Kleene's theorem**, every regular expression has an equivalent
Deterministic Finite Automaton (DFA) that accepts exactly the same
language. `backend/app/dfa.py` makes this concrete instead of just
citing it: it hand-simulates a DFA — formally a 5-tuple
`(Q, Σ, δ, q0, F)` — for identifiers and for numbers, character by
character, and returns the full path of states visited. The **DFA
Visualizer** page in the frontend lets you type a string and literally
watch the automaton walk from state to state, landing on an accepting
state (success) or the dead state `qE` (rejection).

- **Identifier DFA**: `q0 → q1` on a letter/underscore (accepting,
  self-loops on letters/digits/underscore), anything else → dead state `qE`.
- **Number DFA**: `q0 → q1` on a digit (accepting integer state), optional
  `q1 → q2 → q3` for a decimal point followed by more digits (accepting
  float state).

**3. Lexical Analysis**
`lexer.py` is the "scanning" phase of a compiler: it reads raw query
text left to right and groups characters into the smallest meaningful
units — *tokens* — discarding whitespace. This is the direct,
practical implementation of the regular-expression/DFA equivalence
above: a lexer is essentially many small DFAs (one per token type)
run in parallel with longest/first match winning.

**4. Context-Free Grammar (CFG)**
Regular expressions can't express nested or sequential structure like
"SELECT ... FROM ... WHERE ...". That needs a grammar with
non-terminals and production rules — more expressive than a regular
language, one level up the Chomsky hierarchy. The grammar for this
project's query language (in `backend/app/grammar.py`):

```
<query>        ::= SELECT <columns> FROM <table> <where_opt> ;
<columns>      ::= "*" | <identifier> <columns_tail>
<columns_tail> ::= "," <identifier> <columns_tail> | ε
<table>        ::= <identifier>
<where_opt>    ::= WHERE <condition> | ε
<condition>    ::= <identifier> <operator> <value>
<operator>     ::= "=" | ">" | "<" | ">=" | "<=" | "!="
<value>        ::= NUMBER | STRING | <identifier>
```

**5. Syntax Validation**
Because this grammar is **LL(1)** — every production can be decided
by looking at just one token of lookahead, with no left recursion —
a simple **recursive-descent parser** (one Python function per
grammar rule) is enough to validate it. This is exactly how the
"syntax analysis" phase of a real compiler works, just for a much
smaller language. When a query doesn't match the grammar, the parser
reports precisely which rule failed and why (missing `SELECT`,
missing `FROM`, missing table name, invalid identifier, invalid
operator, missing semicolon, ...).

## Notes

- This project intentionally keeps everything hand-written and simple
  enough to explain line by line in a viva — no external SQL parsing
  library, no query execution, no hidden "magic" validation.
- CORS is left open (`allow_origins=["*"]`) in `main.py` since this is
  a local student project; tighten it if you ever deploy it publicly.
